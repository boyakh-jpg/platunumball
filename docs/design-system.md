# 2026-06-27 모집/경기 원격 로딩 상태

## 2026-07-25 공용 체크박스 iOS 외형

1. 모든 페이지의 checkbox는 브라우저 native 외형을 사용하지 않는다. `18px` 둥근 사각형으로 고정하고 iOS Safari의 다크 모드에서도 선택·미선택 크기와 형태가 같아야 한다.
2. 미선택 상태는 중립 control 배경과 테두리, 선택 상태는 주황 배경과 흰색 체크를 사용한다. 검은 원·검은 덩어리 또는 상태별 크기 변화는 허용하지 않는다.
3. checkbox는 공용 primitive가 외형을 소유한다. 화면별 CSS는 배치만 조정하며 focus 표시와 disabled 구분을 제거하지 않는다.

## 2026-07-25 선택 control 의미·동일 행 정렬

1. 독립적인 사용 여부와 확인 동의는 checkbox를 사용한다. 같은 정책 묶음에서 값을 명시적으로 비교해야 하는 필드는 `label + select` 또는 짧은 segmented control을 사용하며 제목 없는 checkbox를 섞지 않는다.
2. 방 생성·수정의 `경기 공 준비`와 `조끼 준비`, 경기 규칙의 `2점 차 승리`, 매칭 참가의 `진영`과 `참가 상태`는 같은 높이의 명시형 선택 필드로 표시한다. 저장 payload의 기존 enum·boolean 자료형은 바꾸지 않는다.
3. 버튼·input·select처럼 직접 조작하는 control만 같은 행에 놓이면 세로 중심선을 맞춘다. label·도움말·오류를 포함한 field grid, 여러 줄 확인문, textarea, 카드와 목록은 상단 정렬을 유지한다.
4. input·select·textarea의 focus는 모든 페이지에서 주황색 공용 focus ring을 사용한다. 화면별 초록 focus나 checkbox `accent-color` override를 추가하지 않는다.

## 2026-07-25 전역 타이포그래피 굵기

1. 모든 페이지의 사용자 표시 텍스트는 `--font-weight-body: 600`을 최저 굵기로 사용한다. 본문, 설명, 상태, 입력값, placeholder, 버튼, 하단 메뉴까지 같은 기준을 적용한다.
2. 제목·강조·스포츠 디스플레이의 기존 `700~950` 위계는 유지한다. 색상이나 opacity가 약한 보조 문구도 굵기를 `600` 아래로 낮추지 않는다.
3. 아이콘, 로고, 일러스트처럼 실제 문자가 아닌 그래픽만 굵기 기준에서 제외한다. CSS와 inline style에 `600` 미만의 사용자 표시 글자 굵기를 추가하지 않는다.

## 2026-07-25 대회 심판·지역 승인 UI

1. 대회 생성 화면은 참가팀 선택 뒤 같은 단계에서 필수 심판 수, 심판 검색, 선택한 심판, 중립 심판 커버리지 오류를 표시한다. 주최자 자격 오류와 심판 부족 오류를 생성 버튼 직전에 숨기지 않는다.
2. 대회 상세 상단 요약은 팀 승인, 심판 승인, 생성 경기, MMR 승인 계수를 같은 위계로 표시한다. 네 항목은 데스크톱에서 한 행, 좁은 화면에서는 가로 스크롤 또는 안전한 줄바꿈으로 잘리지 않아야 한다.
3. 심판 초대·승인·거절, 지역관리자 승인·비승인, 주최자의 지역 비승인 개최는 각각 역할이 보이는 별도 action으로 표시한다. 지역 비승인도 심판이 필수라는 안내를 승인 action 바로 옆에 둔다.
4. 경기별 심판 배정은 실제 대진의 양 팀과 무관한 승인 심판만 선택지로 보여준다. 모바일에서는 대진, 심판 선택, 배정 버튼을 한 열로 쌓고 다크·라이트 surface를 함께 지원한다.

## 2026-07-25 대회 일정 잠금·모바일 입력

1. 대회 일정 control은 최초 저장 전 `일정 설정`, 최초 저장 뒤 `일정 수정`을 표시한다. 실제 수정 1회를 사용했거나 어느 팀이든 출전 명단을 제출하면 수정 버튼 대신 `일정 수정 1회 사용` 또는 `출전 명단 제출 후 잠금`을 표시한다.
2. 대회 경기 모달의 출전 명단 구성은 현재 directory에 팀장 row가 빠져 있어도 대회 팀 스냅샷으로 보강한다. `confirmedAt`만으로 팀장 control을 숨기지 않으며, 일정이 지정된 예정 경기에서는 A/B 슬롯보다 먼저 배치한다.
3. iPhone을 포함한 `720px` 이하 일정 form은 날짜·시간·구장·액션을 한 열로 쌓는다. native 날짜·시간 picker를 유지하되 form과 각 control에 논리 너비 `100%`, `min-inline-size: 0`, `max-inline-size: 100%`를 적용해 카드 테두리를 넘지 않게 한다.

## 2026-07-25 입력창 내부 검증 안내

1. 숫자 control은 사용자가 기존 값을 전부 지우고 새 값을 입력할 수 있어야 한다. 편집 중 값을 자동으로 최솟값에 맞추지 않는다.
2. 필수·최솟값·최댓값 오류는 공용 `InlineValidatedInput`으로 입력창 오른쪽 안에 위험 색상으로 표시한다. 오류 상태는 테두리와 `aria-invalid`, 연결된 설명으로도 전달한다.
3. 숫자 입력 오류가 있으면 룰 요약 대신 입력 확인 안내를 표시하고 생성·수정 저장을 비활성화한다. 유효해진 즉시 정상 요약과 저장 상태로 복귀한다.
4. 구체적인 만남 장소는 빈 값일 때 입력창 안에 `필수`, 공백 제외 한 글자일 때 `2자 이상`을 표시한다. 예시 placeholder와 필수 안내를 한 문장에 중복하지 않는다.
5. 입력창 내부 메시지는 숫자 stepper, 실제 입력값, 모바일 너비와 겹치지 않아야 하며 다크·라이트 모두 `--danger` token을 사용한다.

## 2026-07-25 라이트 테마 중립 surface·선택 상태

1. 라이트 테마의 일반 카드, 패널, 입력, 팝오버, 하단 메뉴는 민트·청록 tint를 사용하지 않는다. `--ui-card-*`, `--ui-control-*`의 아이보리·흰색·중립 회색 surface를 사용한다.
2. 메뉴 활성, 선택 행, 선택 카드, 필터 활성, focus ring은 `--rb-orange`와 `--ui-selectable-*` token으로 표시한다. 기능 CSS에서 초록 선택색을 다시 선언하지 않는다.
3. 초록은 준비 완료, 승인, 성공처럼 의미가 고정된 상태와 팀 고유색에만 사용한다. 일반 section eyebrow와 선택 checkbox·radio는 주황색을 사용한다.
4. 이 기준은 과거 라이트 테마의 민트 surface·메뉴 설명보다 우선한다.

## 2026-07-24 QR 출석·후보 교체·사후 명단 UI

1. 공개 매칭의 공용 `RuleSelector`는 경기시계를 사용할 때만 `QR 출석 사용` switch를 표시한다. 공개 경쟁전은 경기 전 구성·현장 픽업 모두 기본 활성화하고 공개 친선전은 기본 비활성화한다. 생성·수정 화면은 같은 중앙 규칙을 표시한다.
2. 체크인 단계의 방장·배정 심판 화면은 QR, 5분 교체 남은 시간, A/B 정상·지각·대기 수, 미출석 정리 또는 축소 action을 한 panel에 표시한다. 정리 action은 경기 10분 전부터 열고 방 수정 횟수를 쓰지 않는다는 확인 문구를 제공한다.
3. 경기시계 QR은 기존 점수·시간을 가리지 않는 오른쪽 아래 보조 영역에 최소 스캔 크기로 표시한다. 모바일에서는 점수 행 아래의 독립 행으로 내려 가로 overflow와 A/B 점수 겹침을 막는다. 집중 화면에서도 같은 정보 순서와 스캔 가능 크기를 유지한다.
4. live 교체 panel은 운영 권한이 있는 사이드의 후보 전체를 보여주고 `교체 대상·사유·교체`를 한 행으로 묶는다. 모바일에서는 control이 잘리거나 후보 한 명만 접근 가능해지면 안 된다.
5. postgame 명단 panel은 A/B 선택, 가입 선수 검색, 무기명 이름 입력, 이번 단계에서 추가한 선수의 제거를 한 surface에서 제공한다. 추가 선수의 `MMR 제외` 상태를 즉시 표시하고 공용 control/card token으로 다크·라이트를 함께 지원한다.
6. 방장·배정 심판이 준비 panel 또는 경기시계의 QR을 누르면 화면 중앙의 적당한 크기로 확대한다. 배경 클릭, `Escape`, 닫기 버튼으로 원래 화면에 복귀하며 원본 QR 배치는 바꾸지 않는다.
7. 출석 현황 새로고침은 요청 중 `갱신 중`, 성공 뒤 `새로고침 완료`와 경과 시간을 표시한다. 15초 자동 갱신도 마지막 갱신 시각을 표시해 사용자가 최신 상태인지 확인할 수 있게 한다.
8. QR 스캔 뒤에는 구형 단독 경기방이 아니라 매칭 목록과 같은 공통 방 모달을 연다. 모달 제목 아래에 처리 중·정상 출석·지각 후보·실패 결과를 표시한다.

## 2026-07-24 공통 surface·CTA·목록 카드 기준

1. 홈·일정·매칭·플레이·팀·프로필의 일반 content surface는 `Card`/`.ui-card`를 기준으로 한다. 배경, 테두리, radius, shadow, padding은 `--ui-card-*`와 `--ui-card-padding`에서만 정하고 page CSS가 같은 외형을 다시 선언하지 않는다. 이미지가 핵심인 hero·랭크 spotlight만 예외다.
2. 일반 버튼은 `Button`/`.ui-button`의 `md 42px`, `sm 34px` 높이를 사용한다. 버튼과 상태 badge의 라벨은 기본 한 줄이며 모바일에서도 글자 단위로 접지 않는다. 공용 `.ui-action-row`의 자식은 내용 너비를 유지하고 실제 가로 공간이 부족할 때만 다음 줄로 이동한다. 가로 전체 확장은 `.ui-button-block`만 추가하며 홈·일정·매칭별 CTA class로 높이·색상·radius를 덮지 않는다.
3. 일정·매칭·플레이 목록은 `MatchListCard` 하나를 사용한다. 외부 surface는 `Card`, 내부 요약은 `.ui-panel`, action은 `Button`이 담당하고 `match-list-card.css`에는 grid·gap·줄바꿈·상태 bar 같은 배치만 둔다.
4. `om-match-card`, `om-match-create`, `arena-hero-cta`, `home-search-create-button`, `wide-button`은 폐기한다. 해당 selector를 다시 추가하거나 feature CSS에서 공용 surface·CTA 외형을 덮으면 빌드의 `design-system-guards`가 실패해야 한다.
5. 공통 디자인 변경은 primitive를 먼저 수정해 전 화면에 반영한다. 화면별 예외가 필요하면 정보 구조나 배치 차이인지 먼저 확인하고, 단순 외형 차이면 예외 selector를 만들지 않는다.

## 2026-07-24 점유 슬롯 방 수정 UI

1. 공용 방 모달의 `방 수정`은 모집, 경기, 플레이 진입점에서 같은 `RuleSelector`, `MatchOperationsPolicyFields`, `MeetingPointFields`, 출전·후보 정원 control과 구장 selector를 사용한다. 방 종류별 수정 모달을 따로 만들지 않는다.
2. 수정 draft는 현재 구장 ID·이름을 첫 option으로 보존한다. 전체 구장 directory가 아직 로드되지 않았다는 이유로 빈 selector를 표시하거나 저장 시 구장을 지우지 않는다.
3. 일반 구성의 출전 정원과 후보 정원은 현재 양 사이드의 실제 점유 수를 각각 검증한다. 줄일 수 없는 값은 저장 버튼을 비활성화하고 `현재 출전 인원`, `현재 후보 인원`을 분리해 안내한다. 현장 픽업은 `현재 참가 인원`과 `변경 후 전체 정원`만 비교하며 후보 문구를 쓰지 않는다.
4. 저장 중에는 버튼을 `저장 중`으로 바꾸고 중복 저장과 닫기를 막는다. 서버 성공 때만 수정 panel을 닫으며 실패하면 입력값과 panel을 유지하고 사용자가 이해할 한국어 원인을 같은 panel에 표시한다.
5. 모집방에는 `현재 참가 슬롯은 그대로 유지됩니다.`, 확정 경기방에는 `저장하면 경기 전 동의를 다시 받아야 합니다.`를 표시한다. 모집방 참가자에게 재수락을 요구한다고 안내하지 않는다.
6. 출전 정원, 후보 정원, 구장, 경기 방식 control은 공용 auto-fit field grid를 사용한다. 데스크톱·모바일과 다크·라이트에서 한 control만 다음 줄에 남아 과도한 빈 공간이나 가로 overflow를 만들면 안 된다.
7. 확정 경기의 수정 panel은 경기 상세 API에서 받은 최신 값을 표시한다. 닫힌 모집방의 이전 규칙을 다시 보여주거나 저장해 최신 경기 값을 덮어쓰면 안 된다.

## 2026-07-23 매칭 생성 분류·기록방·반응형 UI

1. 매칭 생성의 첫 선택은 `경기 목적`과 `팀 구성` 두 축으로 분리한다. 경기 목적은 `친선전/경쟁전`, 팀 구성은 `경기 전 구성/현장 픽업`이며 네 선택을 한 radiogroup에 섞지 않는다.
2. 경기 목적 카드에는 MMR 반영 여부만 설명한다. 후보 출전정책은 후보 정원 아래 한 곳에서만 표시하고 선택값을 목적 카드에 반복하지 않는다.
3. 후보 정원 `없음/1명/2명/3명`은 네 칸 고정 grid와 줄바꿈 없는 짧은 라벨을 사용한다. 좁은 화면에서도 한 버튼만 다음 줄로 떨어뜨리지 않는다.
4. 생성 하단 `취소하기/이전/다음`은 공용 기본 버튼 높이를 사용한다. `이전`과 휴대폰 뒤로가기는 현재 플로우의 전 단계로 이동하고 `취소하기`만 생성 화면을 닫는다. `420px` 이하의 첫·마지막 단계는 남는 반쪽 칸 없이 두 action을 한 줄에 배치한다.
5. 경기 기록방은 단일 화면이다. 구장 검색·선택과 선택 취소를 같은 기록 메모 카드에 두고, 생성하지 않은 규칙 카드·규칙 요약·규칙 pill을 방 모달에 표시하지 않는다.
6. 생성 페이지 hero는 일반 경기 방 만들기에 전용 체육관 배경(`--bg-create`), 경기·개인 기록에 기록 배경을 사용한다. 다크·라이트 모두 공용 page hero 배경·crop token을 사용한다.

## 2026-07-23 CSS primitive와 lint 강제

1. `tokens.css`는 색상, border, radius, shadow, control 높이, modal surface의 유일한 시각 원본이다. 새 UI는 raw 색상·수치 대신 `--ui-*`, `--rb-*`, `--radius-*` token을 사용한다.
2. 공용 primitive는 `.ui-card`, `.ui-button`, `.ui-badge`, `.ui-panel`, `.ui-control`, `.ui-action-row`, `.ui-modal-shell`, `.ui-modal-section`, `.ui-status-strip`을 기준으로 한다. 새 page selector가 같은 표면·테두리·높이를 다시 정의하지 않는다.
3. feature CSS는 grid, flex, gap, 정렬, 배치, 반응형처럼 해당 화면의 layout만 정의한다. card/control/button/modal의 색상, border, radius, shadow, 높이는 primitive selector에 먼저 반영한다.
4. 공용 방 모달 skin과 panel은 한 공용 room-modal style layer에서 한 번만 import한다. `globals.css`, 모집, 경기, 플레이 page CSS에 같은 room selector를 중복 추가하거나 뒤쪽 override로 맞추지 않는다.
5. Stylelint는 `tokens.css` 밖의 hex·rgb·rgba 직접 색상, primitive 밖의 임의 `border-radius`, 공용 control 밖의 고정 button/input 높이, allowlist 밖의 `!important`, 동일 scope의 중복 selector를 오류로 처리한다. 원형의 `50%`, pill의 공용 token, 이미지 overlay, native control·portal 위치 보정은 명시적 allowlist만 허용한다.
6. CSS 변경은 lint 뒤 `desktop/mobile × dark/light × pickup_pool/pickup_assignment/prearranged/live/match_record` 조합을 시각 검증한다. 한 조합이라도 overflow, 잘림, 겹침, primitive 이탈이 있으면 완료로 보지 않는다.
7. 설계 문서에서 최신 규범과 충돌하는 과거 selector·수치 기록은 구현 근거로 사용하지 않는다. 현재 규범 section을 먼저 고치고 변경 이력은 별도 이력으로만 보존한다.

### 교차 페이지 CSS 감사 기준

1. 홈의 `매칭 만들기`와 `경기 기록하기` CTA는 모든 화면 너비에서 동일한 두 열과 표준 간격을 유지한다.

## 2026-06-28 페이지 로딩 바운딩볼

5. 경기 화면 로딩 중에는 일정 카드, 상단/달력 숫자 카운트를 숨기고 `내 일정 확인 중`과 `확인 중`만 표시한다.

## 최상위 원칙

1. 같은 기능은 같은 모양이어야 한다.
   - 공개방/비공개방 카드가 내용은 달라도 구조는 같아야 한다.
   - 매칭 메뉴와 경기 메뉴에서 같은 방은 같은 모달로 보여야 한다.

2. 화면마다 다른 히어로 구조를 만들지 않는다.
   - 홈, 경기, 매칭, 진행, 팀, 나, 설정은 같은 header/hero 기준을 쓴다.
   - 위치, 여백, 글자 크기, 배경 크롭 기준을 통일한다.

3. 라이트/다크는 색과 이미지 시간대만 다르다.
   - 같은 메뉴는 같은 그림 구도와 같은 위치를 쓴다.
   - 라이트는 낮 이미지, 다크는 밤 이미지.
   - 배경 두 장 겹쳐 쓰지 않는다.

4. 카드 안 카드 금지.
   - 카드 안쪽에는 작은 패널을 둘 수 있지만, 떠 있는 카드처럼 보이게 중첩하지 않는다.
   - 구분은 배경 단계, border, padding으로 한다.

5. 정보는 카드에서 줄이고 모달에서 푼다.
   - 목록 카드에 참여자 전체를 넣지 않는다.
   - 목록은 상태/일시/구장/방식/방보기 중심.

6. 모바일 우선으로 깨짐을 막는다.
   - 가로 스크롤 금지.
   - 큰 요약 패널은 모바일에서 제거.
   - 필터는 가로 스크롤이 아니라 줄바꿈.

4. 참가 방식

목록 카드 배지 색은 `MatchListCard`에서 아래 3색으로 정규화한다. 호출 화면이 다른 tone을 넘겨도 목록 카드에는 별도 색을 추가하지 않는다.

| 의미 | 색 |
| --- | --- |
| 단계·정보 (`waiting`, `locked`, `live`, `record`, 경기 방식) | blue |
| 처리 필요 (`checkin`, `postgame`, `dispute`, 희망 상대) | orange |
| 종료·보조 정보 (`cancelled`, `void`, 공개 여부, 참가 방식, 경기 종류, 심판) | neutral |

`green`, `gold`, `violet`, `danger` tone은 공통 목록 카드 안에서 각각 `blue` 또는 `orange`로 변환한다. 일정·매칭·플레이 목록은 모두 이 규칙을 공유한다.

- 공개확정
- 일반
- 사전등록 남발
- FLOW 접두어
- 카드 제목에 상태 중복 표기

- 후보 슬롯만 다른 컴포넌트처럼 보이는 것.
- 프로필 텍스트 때문에 카드 높이가 늘어나는 것.
- 관리 버튼 때문에 슬롯 줄이 깨지는 것.

슬롯 표시 순서:

1. 왕관/역할 표시.
2. 포지션 아바타.
3. 이름.
4. 포지션.
5. 파티/개인 참여.
6. READY/WAIT.

왕관 기준:

- 노란 왕관: 방장.
- 파란 왕관: 사이드장/파티장.
- 같은 슬롯에서 겹치면 노란 왕관만 표시.
- 확정 경기에서는 유효 사이드장 왕관만 표시하고 모집 엔트리 파티장 왕관을 중복 표시하지 않는다.
- 방장이 속한 사이드에서는 방장 노란 왕관만 표시하고 별도 사이드장 파란 왕관을 함께 표시하지 않는다.
- 팀 주장은 팀 화면에서만 표시하고 경기 슬롯 왕관으로 쓰지 않는다.

## 아바타 원칙

1. 슬롯은 포지션 아바타 사용.
2. 티어는 배경 엠블럼으로만 표시.
3. 티어 텍스트/뱃지는 슬롯 안에서 제거.
4. hover 카드에는 티어 상세 유지.
5. `object-fit: cover`.
6. `contain` 금지.
7. 하반신은 숨기고 얼굴~상체 중심.
8. 아바타가 슬롯 크기를 키우면 안 된다.
9. 상하좌우 자른 경계가 칼로 자른 느낌이면 안 된다.
10. PG/PF는 공이 보이게 조금 줄인다.
11. C는 엠블럼을 가리지 않게 줄인다.

## 파티 시각화

1. 파티는 전체 테두리로 묶는다.
2. 파티 내부 슬롯 간격은 변하지 않는다.
3. 2명 이상일 때만 파티 표시.
4. 혼자 남은 파티는 표시하지 않는다.
5. `o-o-o` 느낌의 연결선을 넣는다.
6. 연결선은 텍스트와 아바타를 가리지 않는다.
7. 모바일에서는 연결선보다 전체 배경/테두리 우선.

## 프로필/호버 원칙

데스크톱:

- hover로 카드 표시.
- 클릭하면 카드 고정.
- 카드 고정 중 다른 hover 카드 금지.

모바일:

- 탭/길게 누르기로 카드 표시.
- 프로필 페이지 이동은 카드 안 `프로필 보기`.
- 선수/팀/구장/심판 모두 같은 규칙.

팝업:

- 최상단 포털.
- 부모 카드에 잘리면 안 됨.
- 아래 공간 없으면 대상 상단 기준 위로 표시.
- 외부 클릭 시 닫힘.

## 라이트 모드 원칙

1. 다크용 검은 투명 박스를 그대로 쓰지 않는다.
2. 카드와 내부 패널 색 차이가 보여야 한다.
3. 작은 글씨 대비를 확보한다.
4. 아바타 배경 경계가 보이면 마스크/배경을 조정한다.
5. 배경 사진은 낮 이미지.
6. 테두리만으로 구분하지 않고 배경 단계도 둔다.
7. 하단 메뉴는 회색 덩어리로 보이지 않게 밝은 민트/블루 계열 flat surface를 쓰고 gradient를 넣지 않는다.

## 모바일 원칙

1. 가로 스크롤 금지.
2. 하단 메뉴 한 줄.
3. 하단 메뉴가 본문을 가리면 본문 padding-bottom 조정.
4. 필터 버튼은 줄바꿈.
5. 큰 요약 패널 제거.
6. 카드 내부 긴 정보는 접거나 숨긴다.
7. 기록판은 한 화면에 최대한 5명 보이게.
8. 개인활약은 3칸 x 2줄.
9. 모달 액션 버튼은 손가락으로 누르기 충분한 높이.
10. 주소창/하단 메뉴 때문에 가려지는 영역 고려.
11. 기록방 요약은 점수/개인활약/파울을 말줄임하지 않고 줄바꿈으로 전부 읽히게 한다.
12. 모바일 슬롯 액션/초대 팝업은 슬롯 좌표에 매달지 않고 화면 안쪽 중앙 sheet로 띄운다. 초대 검색 결과는 팝업 안 inline 목록으로 크게 보여서 선택 버튼이 숨거나 화면 밖으로 잘리지 않게 한다.
13. 달력 날짜 칸은 경기 수 배지가 있어도 행 높이가 바뀌지 않게 고정한다.
14. `dispute` 방 모달은 경기 관계자가 점수판을 열람하고 새로고침할 수 있다. 점수판 수정/저장은 심판 또는 방장에게만 보이며 저장 결과 메시지는 기록판 안에 짧게 표시한다.
15. `record` 방 모달은 읽기 전용이다. 채팅 입력, 슬롯 관리, 초대, 방 수정 버튼을 보이지 않는다.

## 홈 디자인 원칙

홈은 대시보드가 아니라 액션 허브다.

구성:

1. 검색/빠른 진입.
2. 처리 필요.
3. 내 일정 요약.
4. 최근 기록.
5. 나 메뉴 기록 화면은 최근 6개월 상세 기록과 날짜별 count를 먼저 보여준다. 6개월 초과부터 최근 5년 기록은 전체 상세 카드가 아니라 텍스트/집계형 목록으로 분리한다.
6. 팀/랭킹 요약.

원칙:

- 검색 기록 영역 제거.
- 처리 완료된 액션은 즉시 사라짐.
- 단순 대기중 방은 홈 액션에 넣지 않음.
- 모집방 목록과 결과 승인 대기 목록은 홈에서 표시하지 않음.
- 카드 그라데이션 혼자 튀지 않게 통일.
- 랭킹/모드별 티어는 2x2 기준으로 정렬.
- 홈 `매칭 만들기`/`경기 기록하기` CTA는 검색 패널 오른쪽에 같은 크기로 둔다. 랭킹/경기/팀/매칭 중복 빠른 링크는 검색 패널 옆에 두지 않는다.
- 홈 Action Queue의 방 초대 row는 `수락`/`거절`/`보기`를 같은 row 안에 둔다. 모바일에서는 버튼을 줄바꿈해 row 밖으로 넘기지 않는다.
- 검색 입력은 공용 `SearchPicker`를 쓴다. 입력 즉시 아래에 결과를 띄우고, 화면 목적에 맞는 대상만 검색한다.
- 방만들기 심판 초대는 native select가 아니라 공용 `SearchPicker`를 쓰고, 심판 자격이 있는 후보만 검색한다.
- 방만들기 구장 선택은 등록 구장 선택이 필수다. 선택이 없으면 CTA 근처에 차단 사유를 보여주고 생성하지 않는다.
- 설정의 요청 폼은 신뢰도/권한 조건을 제출 버튼 근처에 먼저 보여주고, 조건 미달이면 버튼을 비활성화한다.

## 경기/매칭 디자인 원칙

경기:

- 내 일정 중심.
- 캘린더와 목록 정렬 일치.
- 과거 필터는 달력 표시 범위.
- 확정 이후 방은 경기 메뉴에서 같은 모달로 열림.

매칭:

- 대기방 중심.
- 방 카드에서 참여자 제거.
- 필터는 접기 가능.
- 첫 목록은 내 지역 중심이다. `전체 지역` 토글을 기본 필터로 두지 않고, 나중에 시군구 선택 필터로 확장한다.
- DB 기본 제목 `모집방`은 사용자가 쓴 방제처럼 카드 제목으로 강조하지 않는다.
- 모바일 큰 표시판 제거.
- 방보기 버튼은 명확하게.

## 진행 디자인 원칙

1. 진행 중/기록 필요 경기와 확정 후 24시간 이내 평가 가능한 경기만 보여준다.
2. 예정 경기에는 기록판을 보여주지 않는다.
3. 기록 확정 후 24시간이 지난 경기는 경기 메뉴에서 숨기고 나/팀 기록 화면에서만 보여준다.
4. 모바일 기록판은 촘촘하되 터치 가능해야 한다.
5. 점수는 자동 합산이 보이게 한다.

## 팀 디자인 원칙

1. 팀 카드는 엠블럼 중심.
2. 프로필 사진 장식 제거.
3. 골드3 같은 텍스트 티어는 줄이고 엠블럼으로 표시.
4. 즐겨찾기 버튼은 카드 핵심 흐름을 방해하면 제거.
5. 멤버 행은 이름/포지션/역할만 정렬.
6. 오버플로우 금지.
7. 팀 허브 히어로 스타일은 유지 가능.
8. 새 팀명은 경기/매칭 방 요약 박스 기준으로 14자를 넘기지 않는다.
9. 팀 만들기 홈 코트는 native select가 아니라 방 만들기와 같은 구장 전용 `SearchPicker` 검색 기준을 쓴다. 검색창은 선택값과 분리해 비워 두고, 즐겨찾기 또는 추천 구장을 focus popup 안에 보여주며 결과에는 주소를 표시한다. 홈 코트 선택은 한 팀당 하나다.
10. 팀 엠블럼 이미지는 원형 공용 `TeamEmblem` 안에서 `object-fit: contain`으로 전체를 보여주고, 카드마다 별도 색상 점을 만들지 않는다.
11. 팀장용 엠블럼 업로드·변경·삭제는 팀 상세의 기존 관리 카드 안에 두며 별도 중첩 카드를 만들지 않는다.
12. 업로드 control은 데스크톱에서 미리보기·설명·액션 한 줄, `720px` 이하에서 액션 한 줄을 아래로 내려 가로 overflow를 만들지 않는다.
13. 업로드 이미지는 투명 여백을 유지한 정사각 WebP로 정규화하고 이니셜 fallback의 크기·테두리·간격을 그대로 사용한다.

## 설정 디자인 원칙

1. 데스크톱에서 좌우 컬럼 높이 균형.
2. 긴 학습자료는 별도 페이지.
3. 신고/심판/구장 등록은 카드 분리.
4. 구장 등록의 주소검색/좌표변환은 같은 폼 안에서 보조 액션으로 배치.
5. 관리자 메뉴 진입은 권한자에게만 보이는 별도 카드로 둔다.
6. 설정 페이지가 세로로 지나치게 길어지면 분리.
7. 즐겨찾기 관리는 나 메뉴가 아니라 설정 메뉴의 전용 카드에서 한다. 프로필/팀/구장/심판은 각 10개 한도를 표시하고, 관련 검색창의 focus popup과 검색 결과 별 토글에 연결한다.

## 관리자 디자인 원칙

1. 관리자 메뉴는 전체 신고를 시간순으로만 쌓지 않는다.
2. 기본 축은 구장별, 플레이어별, 경기별 정렬이다.
3. 왼쪽은 정렬 큐, 오른쪽은 선택 항목 상세로 둔다.
4. 관리자 화면도 일반 콘텐츠 카드 규칙을 따른다.
5. 임명 관리는 `권한 관리` 업무 탭으로 분리하고, 구장/플레이어/경기 검토 큐보다 먼저 쌓아 보이지 않는다.
6. 처리 액션은 선택 상세 안에 배치하고 신고자 피드백을 기본으로 보여준다. 제재 기간과 대상 선택은 제재 액션을 골랐을 때만 보여준다.
7. 플레이어 큐는 신고/요청/제재가 있는 대상만 보여주고 전체 플레이어를 나열하지 않는다.
8. 플레이어, 구장, 경기 심사는 같은 좌우 workbench를 쓰되, 선택 상세 상단에 현재 심사 축과 처리 기준을 짧게 표시한다.
9. 신고가 여러 개면 최종판단 전에 처리할 신고를 select로 고르게 한다.
10. 관리자 임명 카드는 임명, 연장, 회수 액션을 같은 `admin-action-panel` 안에서 처리한다.
11. 처리 액션은 서버 로그가 붙기 전까지 mock 안내를 같이 노출한다.
12. 관리자 기본 진입은 `구장 신청`이며 상단 업무 탭에서 구장 신청, 플레이어 신고, 사용자 운영, 경기 심사, 팀·소속, 권한 관리를 전환한다.
13. 구장 신청 상세는 신청자, 주소, 좌표, 구장 속성, 승인 액션을 먼저 보여준다. 실제 신고가 없으면 공용 신고 처리 폼을 노출하지 않는다.
14. 관리자 큐는 `처리 대기`를 기본으로 열고 승인·기각된 항목은 `전체 이력`에서 확인한다.
15. 구장 승인 상세는 신청 시설명, 자동 표준명, 검색 기준 주소, 핀 기준 실제 주소, 도로명·지번, 좌표, 지도 링크를 한 흐름에서 확인한다.
16. 같은 장소의 등록·신청 코트를 비교 목록으로 보여주고, 주소·지도 확인 및 복수 코트 확인이 끝나야 승인 버튼을 활성화한다.
17. 최고관리자에게만 `MMR·신뢰도` 업무 탭을 추가한다. 사용자별 점수 수정이 아니라 이벤트 반영률과 증감값을 그룹별 숫자 입력으로 조절한다.
18. 정책 입력은 한 카드 안에서 `개인 MMR`, `경기 형식`, `팀 MMR`, `경기 신뢰도`, `방 운영 신뢰도` 섹션으로 구분한다. 섹션을 다시 카드로 감싸지 않는다.
19. 정책 저장 영역은 현재 버전, 변경 사유, 기본값 초안 적용, 저장 상태를 함께 보여준다. 모바일은 필드와 저장 액션을 한 열로 내려 가로 스크롤을 만들지 않는다.
20. 정책 저장은 공통 확인 팝업에서 적용 시점과 비소급 원칙을 다시 확인한 뒤 실행한다.
21. `사용자 운영`은 상단에 전체 사용자, 30일 활동, 검토 필요, 활성 제재, 30일 경고 요약을 두고 아래에는 기존 관리자 표준과 같은 왼쪽 목록·오른쪽 상세 workbench를 사용한다.
22. 사용자 목록은 `주의 신호`와 `전체 사용자`를 분리하고 이름·해시태그·ID·지역 검색과 30건 페이지네이션을 사용한다. 위험 수치는 검토 정렬값이며 자동 처벌 점수처럼 표현하지 않는다.
23. 상세에는 신호 근거, 최근 30일 활동 지표, 현재 제한 종료 시각을 먼저 보여준다. 조치 선택·기간·관리 사유·사용자 안내는 같은 `admin-user-action-panel`에 배치한다.
24. 경고는 한 번에 발송하고, 기간 제재는 범위와 기간을 다시 보여주는 2단계 확정 상태를 거친다. 처리 중에는 중복 실행을 막고 결과를 액션 바로 아래에 표시한다.
25. 사용자 운영 화면은 공용 주황·금색·파랑·중립 토큰만 쓴다. `860px` 이하에서 목록과 상세를 한 열로, `520px` 이하에서 검색 액션과 확인 액션을 줄바꿈해 가로 overflow를 만들지 않는다.
26. 사용자 운영 상세에는 방 다시 만들기 누적·최근 30일·최대 연속 횟수를 기존 통계 그리드에 표시한다. 반복 이력이 있으면 기존 수동 경고 폼에 정중한 권장 문구를 채우는 보조 액션만 제공하고 자동 제재 버튼을 추가하지 않는다.
27. 관리자 큐의 `처리 대기`와 `전체 이력` 숫자는 현재 선택한 모드에만 표시한다. 필터 액션에는 캐시를 우회하는 `새로고침`을 두고 모바일에서는 기존 action row 줄바꿈을 따른다.

## 메뉴 간 디자인 통일 원칙

같은 정보군은 메뉴가 달라도 같은 구조와 같은 표면을 쓴다.

- 기록: 홈 최근 전적, 나 메뉴 최근 기록, 나 메뉴 전체 기록은 같은 `recent-match-row` 행 구조를 쓴다.
- 수치: 팀 카드 기록, 나 메뉴 통계, 홈 요약 수치는 같은 metric tile 구조를 쓴다.
- 필터: 경기 메뉴 필터와 매칭 메뉴 필터는 줄바꿈 가능한 버튼/셀렉트 구조를 쓴다. 가로 스크롤 금지.
- 필터 active 상태는 라이트/다크 모두 배경과 글자색을 같이 지정해 대비를 유지한다.
- 방 목록: 경기 메뉴와 매칭 메뉴 방카드는 같은 요약 박스 구조를 쓴다. 외형 차이는 허용하지만 정보 계층은 같아야 한다.
- 라이트 모드: 회색 면을 기본값으로 쓰지 않는다. 흰색/민트 계열 표면과 명확한 내부 패널 차이를 둔다.
- 카드 내부: 카드 안의 작은 정보 묶음은 inner panel 계층으로 처리한다. 다른 카드처럼 보이게 중첩하지 않는다.

- 경기 메뉴 공개방 카드가 방 목록 카드의 기준이다. 매칭 메뉴 대기방 카드도 같은 `om-match-card` 배치, 같은 요약 박스, 같은 방보기 버튼 구조를 따른다.

2. floating 검색 결과는 `visualViewport`의 resize와 scroll을 모두 따라가며 실제 위·아래 여유 공간 안에서만 높이를 잡는다. 공간보다 큰 강제 최소 높이를 두지 않는다.
3. 홈 검색 패널은 검색 중 뒤쪽 카드보다 높은 stacking 순서를 가진다. 결과 목록이 다음 섹션 아래로 들어가면 안 된다.
4. body scroll lock은 `scrollbar-gutter: stable`과 수동 scrollbar padding을 동시에 적용하지 않는다. 전역 모달이 열린 동안 모달을 포함한 main stacking context는 데스크톱 sidebar와 모바일 bottom navigation 위에 있어야 한다.
5. 데스크톱 프로필 보조 레일은 카드가 최소 `260px`을 확보할 때만 다열로 배치한다. 좁은 보조 레일에서 공유 카드 내용을 잘라 2열을 강제하지 않는다.
6. 알림의 compact 이동 액션은 데스크톱 최소 `34px`, 모바일 최소 `42px` 높이와 중앙 정렬을 사용한다.

## 2026-07-21 팀 관리와 compact 액션 행

1. 팀 상세의 즐겨찾기 액션은 상단 영문 라벨과 같은 행에 두고, 팀 이름은 그 아래 전체 폭을 사용한다.
2. 팀 메뉴의 내 팀 행은 `순위 / 엠블럼 / 팀 정보 / 액션 묶음` 구조를 사용한다. 티어·대표팀 설정·관리 표시는 하나의 액션 묶음으로 유지하며 `관리`만 단독 행으로 떨어뜨리지 않는다.
3. `520px` 이하에서 내 팀 액션 묶음은 한 행 전체를 사용하되 내부 액션은 같은 줄을 유지한다.
4. 팀원 관리와 팀 엠블럼 관리는 별도 section card로 나눈다. 엠블럼 관리 카드는 팀 상세 보조 열의 마지막에 둔다.
5. 좁은 팀 관리 카드에서도 함께 배치할 수 있는 역할 선택·실행 버튼, 엠블럼 2개 선택지, 색상 설정은 2열을 유지한다. 한 항목만 불필요하게 다음 줄로 보내 카드 높이를 늘리지 않는다.
6. 선수 상세의 팀 정보는 히어로가 아니라 별도 왼쪽 `소속 팀` 레일에 둔다. 대표팀은 첫 행과 강조 테두리로 구분하고 다른 소속 팀도 같은 행 규격으로 이어서 표시한다.

## 2026-07-21 화면별 조회·페이지 상태

1. 관리자 화면은 현재 업무 탭과 `처리 대기 / 전체 이력`에 필요한 row만 읽는다. 다른 업무 탭의 빈 결과를 먼저 렌더링하거나 광역 directory 로더 완료를 기다리지 않는다.
2. 관리자 페이지의 추가 결과는 기존 목록 아래 공용 secondary `더 보기` 버튼으로 합친다. 로딩 중에도 현재 카드·선택·스크롤 위치를 유지한다.
3. 선수·팀 directory 검색은 DB filter와 bounded page를 사용한다. 같은 화면·종류·검색어·지역·offset 조합은 짧은 cache를 재사용하되 명시적 새로고침은 cache를 무효화한다.
3-1. 검색어·지역·관리자 탭을 빠르게 바꿔도 늦게 끝난 이전 요청이 현재 `더 보기`와 결과 상태를 덮지 않는다. 목록용 팀 응답은 roster 전체 프로필을 내려받지 않고 팀 상세·경기 생성처럼 실제 명단이 필요한 화면에서만 확장한다.
4. 모집방 모달은 최초 상세 뒤 전체 modal skeleton이나 전역 로더를 반복 표시하지 않는다. 채팅 증분 polling은 기존 메시지와 입력 위치를 유지하는 background 작업이다.
5. 이 조회 최적화는 카드, 버튼, hero, dark/light 색상과 responsive breakpoint를 변경하지 않는다. desktop/mobile에서 결과 수가 달라도 공용 empty/loading/error surface를 유지한다.

## 2026-07-21 plain-text 입력 피드백

1. 채팅·이름·메모·검색 등 사용자 문자열 입력은 plain text만 저장한다. HTML·스크립트 형태를 입력하면 조용히 삭제하거나 변형하지 않고 `HTML·스크립트 코드는 입력할 수 없습니다.`를 표시한다.
2. 일반 한글·영문·숫자·문장부호·이모지와 `<3` 같은 일반 표현은 허용한다. 보안 검사를 이유로 모든 `<`, `>`, 따옴표를 일괄 금지하지 않는다.
3. 화면별 `maxLength`, 숫자 범위, select allowlist는 유지한다. 공용 payload 검사는 그 아래의 최종 안전망이다.
4. 오류 문구는 기존 form helper 영역에 표시하고 별도 경고 modal을 만들지 않는다. 차단으로 카드 높이·버튼 배치·모바일 가로폭이 바뀌지 않아야 한다.

## 2026-07-21 OAuth URL 보안 피드백

1. Discord 연동 복귀 URL에는 `pending` 또는 오류 상태만 표시한다. Discord 사용자 정보, 서명 증명값, token, 사용자 프로필 ID를 query에 렌더링하지 않는다.

3. OAuth callback query는 처리 직후 `history.replaceState`로 제거한다. 데스크톱·모바일, dark·light의 기존 설정 화면 배치는 유지한다.

## 2026-07-24 플레이 방 경기시계

1. 경기시계는 `gameClockEnabled=true`인 경우에만 매칭·경기 메뉴가 공유하는 공통 방 모달의 `live` 단계에 표시한다. 메뉴별 별도 시계 모달을 만들지 않는다.

4. 샷클락은 숫자를 포함한 전체 타일을 초기화 버튼으로 사용하되 경기시간보다 작은 보조 control로 표시한다. 일반 모바일 화면은 최소 136px 터치 영역을 유지하고, 전체화면은 점수판 높이의 일부만 차지하도록 중앙 정렬한다. 주황색 이중 시각 단서인 돌출 border·shadow와 `초기화` 아이콘 라벨을 함께 표시해 버튼임을 분명히 한다. `사용 안 함`이면 타일과 초기화 action을 렌더링하지 않는다. 시작 전 샷클락 선택은 별도 저장 버튼 없이 즉시 저장하며 서버 polling이 선택 중 값을 되돌리지 않는다. 설정 시간은 자동 감소하고 0초에서 정지한다. 공격권 전환은 자동 판정하지 않으므로 담당자가 다음 공격권에 전체 타일을 눌러 초기화한다. 샷클락 외 경기 조작 버튼은 `sm` 크기와 내용 너비를 사용한다.
5. 현재 담당자가 아닌 기기에서는 시계 action을 숨기고 읽기 전용 상태를 표시한다. 담당 변경은 출전 선수 버튼과 확인 메시지를 거친다.
6. 쿼터 종료, 다음 쿼터 시작, 연장 시작, 담당 변경, 경기시계 종료는 확인 메시지를 표시한다. 일시정지·재개·샷클락 초기화는 즉시 동작하되 남은 시간이 0이면 일시정지·재개 버튼을 렌더링하지 않는다.

2. 모바일은 참가자 카드를 1열로 유지한다. action 너비는 같은 열 안에서 균등하게 맞추고 교환 action은 전체 폭을 사용해 빈 반쪽 칸과 가로 overflow를 만들지 않는다.
3. 팀 배정 방식은 데스크톱에서 같은 너비의 grid로 표시한다. 좁은 화면은 2열과 마지막 홀수 action 전체 폭을 사용하고, 더 좁은 화면은 1열로 전환한다.
4. 픽업 슬롯의 기존 `72px` 고정 폭은 유지한다. 작업판 반응형 변경으로 슬롯 자체를 늘리거나 줄이지 않는다.

## 2026-07-24 CSS cascade 정리 기준

1. 운영 CSS에는 `src`, `public`, 공개 HTML에서 사용하지 않는 selector branch를 남기지 않는다. 외부 지도 SDK와 동적 class prefix는 명시적 허용 목록으로 관리한다.
2. 같은 at-rule 문맥의 같은 selector에서 뒤 규칙이 완전히 덮는 앞 선언은 금지한다. 서로 다른 속성을 보완하는 규칙은 cascade 순서가 동작의 일부이므로 강제로 합치지 않는다.
3. `Card`, `Button`, 목록 카드의 공용 표면은 primitive stylesheet가 담당한다. 기능별 stylesheet는 해당 화면의 배치와 상태 표현만 추가한다.
4. `npm run build`와 `npm run test:design`은 미사용 selector와 완전 shadow 선언 검사를 함께 실행한다.
5. CSS 정리는 동작과 배치를 바꾸지 않는 범위에서만 수행하고 desktop/mobile, dark/light의 computed style과 가로 overflow를 비교한다.

## 2026-07-24 전역 stylesheet 모듈 경계

1. `globals.css`는 규칙을 직접 갖지 않는 import 전용 manifest다. 아래 모듈 순서는 기존 cascade와 같은 공개 순서이므로 검증 없이 바꾸지 않는다.
2. `global-foundation.css`는 reset, app shell, navigation, loader와 초기 공용 구조를 담당한다.
3. `global-workflows.css`는 경기 규칙, 분쟁, 설정과 공용 작업 흐름을 담당한다. `global-search-profile.css`는 검색, 프로필, 엠블럼 UI를 담당한다.
4. `global-admin-layout.css`는 관리자와 복합 레이아웃을 담당한다. `global-surfaces.css`는 page hero와 공용 surface 수렴 규칙을 담당한다.
5. `global-visual-system.css`는 최종 theme·responsive 시각 계층을 담당한다. `global-court-controls.css`는 구장, 방 생성, 팀 관리의 후속 control을 담당한다.
6. 새 규칙은 `globals.css`에 추가하지 않는다. 책임 모듈 또는 기존 feature stylesheet에 추가하며 각 전역 모듈은 `4500행`을 넘기지 않는다.
7. build 검사는 manifest 전용 상태, 모듈 크기, import 전체의 미사용 selector와 module 경계를 넘는 완전 shadow 선언을 확인한다.
8. 전역 모듈의 표준 짝수 gap은 `--space-1`부터 `--space-24` spacing scale을 사용한다. `3px`, `5px`, `7px`, `9px`처럼 광학 보정용 홀수값은 필요한 component 안에서만 직접 사용할 수 있다.

## 2026-07-25 알파 온보딩·사용 설명

1. 홈의 `처음 사용하시나요?` 카드는 검색과 `매칭 만들기`·`경기 기록하기` 2열 CTA를 대체하거나 분리하지 않는다. 랭크 hero 다음의 compact 진입 카드로 표시하고 기존 좌·우 rail의 desktop/mobile 순서를 유지한다.
2. 사용 설명은 `/app/guide?chapter=start|matching|live|records|tier|practice`의 6개 챕터를 사용한다. 한 번에 활성 챕터 하나만 표시하고 상단 목차와 이전·다음으로 이동한다. 잘못된 chapter 값은 시작 챕터로 안전하게 표시한다.
3. 각 챕터는 `정체성·매칭·경기 진행·기록 확정·티어·직접 연습` 순서를 유지한다. 기능 설명은 `방 설정 → 선수·팀·심판 초대 → 수락·출석 → 심판·기록원·선수 역할 → 기록 입력·확정`을 먼저 보여준다. 경기시계를 사용하는 일반 공개 매칭방의 선택형 QR 출석은 매칭 챕터에서 출석과 함께 설명하고, 시계·샷클락 같은 보조 기능은 해당 역할 설명 안에 둔다. 일반 설명 챕터는 현재 화면을 직접 캡처한 대표 이미지 한 장, 3~4개의 짧은 단계, 핵심 주의 한 묶음만 표시해 장문 기능 목록을 만들지 않는다.
4. 캡처 이미지는 설명 대상 UI와 같은 챕터에 두고 구체적인 대체 텍스트와 설명문을 제공한다. 진행 챕터의 경기시계 캡처는 실제 공용 시계에서 A/B 기록 점수판과 설정된 샷클락이 함께 보이는 상태를 사용한다. 연습 챕터는 낡은 캡처 복제 대신 실제 공용 모듈을 여는 진행 미리보기와 `연습 경기 시작` CTA를 사용한다. 준비 중 기능, 자동화되지 않은 운영, 기기별 베타를 현재 보장 기능처럼 표시하지 않는다.
5. 온보딩 화면은 공용 `Card`, `Badge`, `ui-panel`, `.ui-action-row`, button primitive와 기존 dark/light 토큰을 사용한다. 본문·설명은 `--font-body`, 단계 숫자만 `--sports-display-font`를 사용한다.
6. 데스크톱과 모바일은 같은 내용 순서를 유지한다. `320px`, `375px`, `768px`, `1024px`, `1440px`에서 가로 overflow가 없어야 하며 액션은 임의로 세로 고정하지 않고 실제 공간이 부족할 때만 공용 규칙으로 접는다. 홈의 기존 검색 CTA 2열 규칙은 바꾸지 않는다.
7. 설정의 홈 안내 카드 옵션과 사용 설명 마지막 장의 `홈에서 사용 설명 안 보기` control은 같은 `showHomeGuideCard` 값을 즉시 저장한다. 이 값은 홈 진입 카드의 표시만 바꾸며 사용 설명 route와 연습 경기는 숨기거나 비활성화하지 않는다. 마지막 `완료` action은 자동으로 이 값을 바꾸지 않는다.
8. 연습 진행 안내는 공용 방 모달 안의 `contextPanel`로 표시한다. 새 방 스킨이나 중첩 모달 테두리를 만들지 않고, 모바일에서는 단계 표시와 보조 action이 가로 overflow 없이 자연스럽게 접혀야 한다. 픽업 출석 보조 action은 출석만 채우고 `팀 나누기 → 배정 확정`은 공용 작업판에서 사용자가 직접 실행하도록 안내한다.
9. 연습 경기의 `현재 역할 화면 · 한 기기 체험` 선택은 실제 방장·심판·출전 선수·후보 선수·A/B 기록원 권한 화면을 한 기기에서 바꾸어 보는 보조 control이다. 현재 경기시계 담당은 선택 option에 `시계 담당`으로 표시한다. 역할을 바꾸면 공용 경기방을 즉시 다시 읽어 새 권한을 반영하며, 시계 담당을 넘긴 뒤에는 새 담당 선수 화면을 직접 선택하기 전까지 기존 화면을 읽기 전용으로 유지한다.
10. 메모리에만 존재하는 연습방 URL은 다른 기기에서 열 수 없으므로 공용 모달의 URL 복사·공유 action을 숨긴다. 방 닫기와 공용 생명주기 action은 그대로 유지한다.
11. 안내용 연습은 단계 사이에 실제 시간을 기다리지 않도록 공용 생성 폼의 `즉시` 일정을 사용한다. `일정 지정`은 비활성화하고 바로 아래에 연습 전용 제한을 명시한다.
12. 방 모달의 출전 슬롯 grid는 1v1·2v2·3v3·5v5의 실제 사이드 정원만큼만 track을 만든다. 확정 경기에서는 사이드장과 파티장 원본을 동시에 표시하지 않고 사이드장 하나만 파란 왕관으로 표시한다. 방장이 속한 사이드에서는 노란 방장 왕관만 표시한다.
13. 픽업 배정 초안·확정 뒤 공용 방모달은 현재 경기의 A/B 출전·후보 명단을 그대로 표시한다. 모집 당시 방장 사이드나 파티 데이터를 다시 합성해 정원보다 많은 슬롯을 만들거나 반대 사이드 인원을 누락하지 않는다.
14. 모바일 연습 안내는 세로 전환 시 역할 선택 control의 데스크톱 flex 기준 높이를 제거한다. 역할 선택과 보조 action 사이에 빈 영역을 만들지 않고 공용 gap만 유지한다.
15. 안내용 연습방은 더미 참가자를 모두 자동 초대 상태로 만들지 않는다. 공용 빈 슬롯 검색과 초대 UI를 한 번 직접 사용하도록 한 자리를 남기고, 나머지 더미는 연습 메모리에서 수락 상태로 채워 반복 작업을 줄인다.
